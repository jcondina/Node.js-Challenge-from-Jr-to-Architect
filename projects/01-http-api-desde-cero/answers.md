## Fundamentals
1. REST is an architectural style for designing networked applications. In this project, REST is used to structure the API endpoints and define how clients can interact with the server. It helps to avoid issues related to tight coupling between the client and server, as well as making the API more scalable and maintainable. By using standard HTTP methods and status codes, it makes it easier for clients to understand and use the API.
2. Status codes are used to indicate the result of an HTTP request, while validation runtime refers to the process of checking the validity of the data being sent in the request body. In this context, status codes are used to communicate the outcome of the request (e.g., success, client error, server error), while validation runtime is used to ensure that the data being sent by the client meets certain criteria (e.g., required fields, data types). Both are important for providing a good user experience and ensuring that the API behaves as expected.
3. Invariants of the domain that should not depend solely on the HTTP layer include business rules and data integrity constraints. For example, if there is a rule that a task cannot be marked as completed if it is already archived, this rule should be enforced in the business logic layer rather than relying on the HTTP layer to prevent invalid requests. This ensures that the core logic of the application is not tightly coupled to the specifics of the HTTP protocol and can be reused in different contexts (e.g., command-line interface, background jobs).

## Design
1. The logic related to contract errors should be located in a middleware or a dedicated error handling layer. This allows for consistent error responses across all endpoints and keeps the route handlers focused on their primary responsibilities (e.g., processing requests and interacting with the data layer). By centralizing error handling, it also makes it easier to maintain and update the error handling logic as needed.
2. The public contract that should remain stable even if the internal implementation changes are the API endpoints and their expected request and response formats. This includes the HTTP methods, URL paths, query parameters, and the structure of the request and response bodies. By maintaining a consistent public contract, clients can continue to use the API without needing to make changes on their end, even if the internal implementation of the API evolves over time.
3. In this project, a difficult architectural decision to reverse later on would be the choice of storage mechanism. For example, if we start with a simple file-based storage (like a JSON file) and later decide to switch to a database, it would require significant changes to the data access layer and potentially the business logic layer as well. This is because the way data is read and written would change, and we would need to ensure that all parts of the application that interact with the data are updated accordingly. Therefore, it's important to carefully consider the storage mechanism from the beginning and choose one that can scale with the application's needs. Another architectural decision that could be difficult to reverse is the choice of framework or runtime (e.g., Bun vs Node.js). If we tightly couple our application to a specific runtime, it may be challenging to switch to a different one later on without significant refactoring.

## Debugging
1. To investigate a bug where pagination produces inconsistent results, I would start by reproducing the issue locally. I would create test cases that cover different scenarios of pagination (e.g., different page sizes, different page numbers) and observe the results. I would also check the implementation of the pagination logic to ensure that it correctly calculates the offset and limit based on the page number and page size. Additionally, I would look for any potential issues with the data source (e.g., if tasks are being altered while paginating) that could lead to inconsistent results.
2. For diagnosing problems related to filters, I would need logs that show the incoming requests with their query parameters, as well as the results of applying the filters to the data. Metrics on the number of requests and the distribution of filter values could also help identify if certain filters are causing issues. Traces that show the flow of data through the filtering logic could help pinpoint where things might be going wrong. For example, if a filter is not returning the expected results, I would want to see the input data, the filter criteria, and the output data to understand where the discrepancy is occurring.
3. To reproduce a edge case locally without relying on manual data, I would create automated tests that set up the necessary conditions for the edge case. For example, if I want to test how the API handles a large number of tasks, I could write a script that generates a large dataset of tasks and populates the JSON file with that data before running the tests. This way, I can ensure that the edge case is consistently reproducible and does not depend on manual data entry, which can be error-prone and time-consuming. Additionally, I could use tools like Postman or curl to automate the sending of requests with specific parameters to trigger the edge case in the API.

## Tradeoffs
1. Prioritizing idempotency over simplicity initial means that we would design our API endpoints to be idempotent, meaning that making the same request multiple times would have the same effect as making it once. This can lead to a more robust and predictable API, as clients can safely retry requests without worrying about unintended side effects. However, it may require additional complexity in the implementation, such as generating unique identifiers for resources or implementing logic to handle duplicate requests. On the other hand, prioritizing simplicity initial may allow for a quicker development process and a simpler codebase, but it could lead to issues down the line if clients need to retry requests or if there are edge cases that arise from non-idempotent behavior.
2. One part of the project that I would not optimize yet is the performance of the API. While it's important to have a responsive API, premature optimization can lead to unnecessary complexity and can divert attention from more critical aspects of the project, such as ensuring correctness and maintainability. Instead, I would focus on writing clean and well-structured code, implementing proper error handling, and ensuring that the API meets the functional requirements. Once the core functionality is in place and we have a better understanding of the usage patterns and potential bottlenecks, we can then consider optimizing performance as needed.
3. Introducing layers in the architecture can add complexity and overhead, especially if the system grows in traffic or data. Each layer can introduce additional latency, and if not designed properly, it can lead to issues such as increased response times or difficulties in debugging. For example, if we have a separate data access layer, a business logic layer, and an HTTP layer, we need to ensure that the communication between these layers is efficient and that we are not introducing unnecessary overhead. Additionally, as the system grows, we may need to consider how to scale each layer independently, which can add further complexity. It's important to carefully design the architecture and consider the trade-offs of adding layers, especially in terms of performance and maintainability, as the system evolves.
